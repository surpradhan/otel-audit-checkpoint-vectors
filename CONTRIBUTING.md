# Contributing to otel-audit-checkpoint-vectors

This repo publishes **conformance vectors**. Other people's implementations are
checked against the bytes committed here, so the bar for changing them is higher
than for ordinary code.

## Branch model

`main` is **protected and PR-only** — no direct pushes, no force-push, branch
deletion disabled. Rules apply to maintainers too.

Every change lands via:

```
branch off main → commits → PR → green CI → review → squash-merge
```

Before merge, **all** of the following must hold:
- Every required status check is green
- Branch is up to date with `main`
- All review conversations are resolved
- Any required approving reviews are in place (see note below)

## Required status checks

- `verify`

> **Drift-guard rule:** Whenever you add, rename, or remove a CI job, update
> `.github/workflows/ci.yml`, this block, **and** the GitHub branch-protection
> required-check contexts in the same PR.

The `verify` job runs seven things, and all seven are load-bearing:

1. `gofmt -l` over `go/`, which must report nothing
2. `go vet ./...`
3. The Go validator's unit tests (`go test ./...`), covering the
   `min_format_version` skip rule end to end
4. The Go validator against `vectors.json`
5. A **no-drift** check that `vectors.json` is exactly what the generator produces
6. The independent Python validator against the same file
7. The Python validator's end-to-end unit tests (`py/test_validate.py`), covering
   the same skip rule

Steps 1 and 2 are steps of the existing `verify` job, not jobs of their own, so
the required-checks block above is unchanged — the drift-guard rule is about
adding, renaming or removing a **job**, and branch protection names job
contexts.

## Vector stability discipline (non-negotiable)

**Published vectors are frozen.** Once a vector is on `main`, its canonical bytes,
hashes and signatures must not change. Third parties may already be validating
against them; changing a published vector silently invalidates their conformance
runs without any error they can see.

The following are **breaking vector changes**:

- Any change to the canonical form (field names, field set, types)
- Any change to the tip-sort rule
- Any change to the genesis constant
- Any change to the test key
- Any change to how the chain hash or signature payload is derived

A breaking change requires **all** of:

1. Existing vectors retained unchanged, under a version marker
2. New vectors added alongside rather than in place
3. A note in `README.md` explaining what changed and why

Adding a new vector is not breaking, provided every existing entry stays
byte-identical. The no-drift check will catch you if it does not.

## Two-implementation rule

The Go and Python validators are deliberately independent and share no code. That
independence is the evidence this repo exists to provide.

- A change to one **must** be mirrored in the other in the same PR.
- Never make the Python side import from, or be generated by, the Go side.
- If the two disagree, that is a finding, not a bug to paper over. Work out which
  one is right against RFC 8785 before touching either.

## Commit format

```
<type>: <subject>

<body (optional)>
```

Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`.

**Never add `Co-Authored-By` lines attributing an AI tool.**

## Code review

The author of a PR is never also the one who approves or merges it. "CI is green"
is not the same as "reviewed".

## Development setup

Go 1.25+ and Python 3.12+ with `cryptography`.

```bash
# regenerate and self-check
cd go && go run . gen ../vectors.json && go run . validate ../vectors.json

# independent re-derivation
python3 py/validate.py vectors.json
```

Run both before opening a PR. If `git status` shows `vectors.json` modified after
a regeneration you did not intend, stop: you have made a breaking vector change.

## Branch-protection settings (apply in GitHub UI)

- **Require a pull request before merging**
  - Required approvals: **0 while this is a single-maintainer repo.** GitHub does
    not permit approving your own PR, so requiring 1 with admin enforcement on
    would make merging impossible. Raise this to 1 as soon as a second
    maintainer exists.
  - Dismiss stale reviews when new commits are pushed: ✓
- **Require status checks to pass before merging**
  - Require branches to be up to date: ✓
  - Required checks: every context in the required-checks block above
- **Require conversation resolution before merging:** ✓
- **Require linear history:** ✓ (enforces squash-merge)
- **Do not allow bypassing the above settings (enforce for admins):** ✓
- **Allow force pushes:** OFF
- **Allow deletions:** OFF
