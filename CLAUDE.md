# CLAUDE.md — Agent working conventions for otel-audit-checkpoint-vectors

## What this repo is

**Conformance vectors, not a library.** It publishes test vectors for the canonical
form of a signed audit checkpoint, plus two independent validators that agree on
them byte-for-byte. Other people's implementations are checked against the bytes
committed here. Nothing in this repo is meant to be imported as a dependency.

Companion to [`otel-agent-audit`](https://github.com/surpradhan/otel-agent-audit);
this restates that project's checkpoint mechanism in the OpenTelemetry Audit
Logging vocabulary, over RFC 8785 (JCS) instead of its internal canonical form.
Aimed at the Audit Logging SIG proposal (`open-telemetry/community#2409`).

## Project context

- **Go:** 1.25+, single module in `go/`, depends on `github.com/gowebpki/jcs`
- **Python:** 3.12+, `cryptography`, in `py/`
- **License:** Apache-2.0 (deliberately, to match the OTel ecosystem — the main
  `otel-agent-audit` repo is MIT; do not "harmonise" them)
- **Default branch:** `main` (protected, PR-only)

## Commands

```bash
# regenerate + self-check (Go is the generator and source of truth)
cd go && go run . gen ../vectors.json && go run . validate ../vectors.json

# independent re-derivation, shares no code with Go
python3 py/validate.py vectors.json
```

Run **both** before proposing any change. CI (`verify`) runs both plus a no-drift
check that `vectors.json` equals the generator's output.


Types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `chore`.

**Never add `Co-Authored-By` lines attributing an AI tool.**

## Human-in-the-loop guardrails (non-negotiable)

### Never self-merge to `main`
The agent that authors a PR is never also the one that reviews or merges it.
Stop at "PR open, CI green, awaiting human review." CI-green ≠ reviewed.

### Publishing is the human's action
Creating repos, pushing to public remotes, and posting to upstream OpenTelemetry
threads are outward-facing. Prepare the artifact and hand over the command.

## Vector stability discipline (load-bearing)

**Published vectors are frozen.** Once a vector is on `main`, its canonical bytes,
hashes and signatures must not change. Third parties may already be validating
against them, and changing one silently invalidates their runs with no visible
error.

A change to the canonical form, the field set, the tip-sort rule, the genesis
constant, the test key, or how the chain hash / signature payload is derived is a
**breaking vector change** and requires:

- Existing vectors retained unchanged under a version marker
- New vectors added alongside, never in place
- A note in `README.md` saying what changed and why

If `git status` shows `vectors.json` modified after an unintended regeneration,
stop — that is a breaking change, not a formatting diff.

## Two-implementation rule

The Go and Python validators are independent on purpose. That independence is the
entire evidentiary value of the repo.

- Mirror any change to one in the other, in the same PR.
- Never let the Python side import from or be generated by the Go side.
- If they disagree, that is a **finding**. Resolve it against RFC 8785 before
  changing either.

## Drift-guard discipline

Whenever you add, rename, or remove a CI job, update all three in the same PR:
1. `.github/workflows/ci.yml` — the job definition
2. `CONTRIBUTING.md` — the `<!-- required-checks:start/end -->` block
3. GitHub branch-protection required-check contexts (human applies this in the UI)

## What NOT to do

- Do not edit `vectors.json` by hand. It is generated; edit `go/main.go` and
  regenerate.
- Do not use the test key for anything real. It is a published seed.
- Do not present the placeholder field names as a proposed vocabulary — they map
  to whatever the OTEP settles on, and the README says so deliberately.
- Do not add a third implementation to "confirm" the first two. Two independent
  ones already carry the argument; a third adds maintenance, not evidence.
- Do not relicense to MIT to match the main repo. See Project context.
